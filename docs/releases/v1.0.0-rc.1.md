# Aurevia Health v1.0.0-rc.1

**Release type:** Version 1 release candidate
**Tag:** `v1.0.0-rc.1`
**Tagged commit:** `5d7ef2a3903dcc4980c45630f55869cab34f70cc`
**Release date:** 2026-10-05

Aurevia Health `v1.0.0-rc.1` is the first tagged engineering release candidate for the Version 1 foundation. It establishes a country-neutral, GraphQL-first healthcare platform slice with organization and facility scope, identity and authorization, audit, patient identity, consent/privacy, scheduling, encounters, core clinical records, terminology/interoperability contracts, and repeatable release hardening.

> This release candidate is an engineering foundation validated with synthetic data. It is not a claim of regulatory compliance, production certification, or suitability for real patient care without deployment-specific security, privacy, clinical-safety, legal, operational, and jurisdictional review.

## Highlights

### Trust, tenancy and identity

- organization, health-system, facility and department hierarchy;
- server-controlled country profiles with inherited operational settings;
- Laravel Sanctum first-party session authentication;
- organization memberships, role permissions and facility scope;
- server-side authorization independent of Angular route state;
- structured allowed/denied authorization evidence;
- restricted audit viewing.

### Patient identity and privacy

- internal ULID-based patient identity;
- typed patient identifiers without using national identifiers as database primary keys;
- secure patient search;
- explainable duplicate candidates and non-destructive merge review;
- persisted consent grant/revocation lifecycle;
- privacy decision boundary;
- time-bounded break-glass treatment access with reason and audit evidence.

### Scheduling and encounters

- facility-scoped appointment types and resources;
- timezone-safe booking;
- patient/resource conflict checks;
- retry-safe idempotent booking behavior;
- reschedule and cancellation history;
- waitlist foundation;
- patient/facility-bound encounters;
- explicit encounter lifecycle with guarded transitions.

### Core clinical record

- problem list;
- allergy foundation;
- observations and vitals;
- encounter-bound clinical notes;
- draft/sign lifecycle;
- signed-note immutability;
- append-only addenda and corrections;
- provenance and patient timeline.

### Terminology and interoperability contracts

- terminology concepts with multiple codings;
- explicit coding-system versions;
- replaceable terminology-mapping contract;
- mapping behavior that does not guess absent translations;
- FHIR R4 `4.0.1` exchange anti-corruption mapper;
- correlation-aware interoperability contract preview;
- no coupling of internal persistence models to FHIR resources.

### Release engineering

- repeatable release-candidate validation scripts;
- clean-database migration rehearsal;
- local PostgreSQL backup/restore rehearsal;
- Composer and production npm dependency audits;
- synthetic end-to-end V1 acceptance workflow;
- local application-layer performance baseline;
- source-level and manual accessibility baseline;
- production configuration template and proxy/host hardening;
- GitHub Actions Quality workflow.

## Known Version 1 boundaries

This release intentionally does **not** claim or provide:

- a complete inpatient nursing system;
- full admission/transfer/discharge and bed-management workflows;
- a complete laboratory information system;
- production PACS/DICOM integration;
- a complete medication prescribing/dispensing/eMAR system;
- surgery/perioperative workflows;
- a patient portal;
- country-specific claims or reimbursement implementations;
- a production FHIR/HL7/DICOM transport platform;
- automatic SNOMED CT / LOINC / ICD translation;
- production terminology-server integration;
- a production AI assistant;
- formal penetration-test certification;
- jurisdiction-specific compliance certification.

Those boundaries are deliberate. Version 2 planning extends care-delivery workflows while preserving the V1 authorization, privacy, audit, provenance, signed-record and tenant-isolation invariants.

## Upgrade and compatibility notes

`v1.0.0-rc.1` is the first tagged RC, so there is no earlier tagged Aurevia Health RC upgrade path to preserve. For development environments:

1. use the tagged commit or a later compatible `main`;
2. install Composer and npm dependencies from the committed lockfiles;
3. run the documented database migrations;
4. use synthetic development data only;
5. review `.env.production.example` before any production-like deployment;
6. rerun the release gates after environment-specific configuration changes.

Do not treat this RC as authorization to process real patient data.

## What comes next

Version 2 is planned as a **care-delivery expansion**. It will build outward from the V1 trust foundation into care teams and tasks, clinical orders/results, inpatient ADT and bed flow, nursing, emergency workflows, medication safety, diagnostics, and a new hardening/release-candidate gate.

See [`../../version_2_milestones.md`](../../version_2_milestones.md) for the planned sequence.
